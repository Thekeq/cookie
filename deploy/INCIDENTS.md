# Runbook: инциденты

Потеря данных — в `RUNBOOK.md`. Здесь всё остальное: что делать, когда сервис
жив, но работает неправильно.

Порядок в каждом разделе один и тот же: **как понять → что сделать сейчас →
чего НЕ делать → как убедиться, что прошло**. «Чего не делать» стоит выше
разбора причин намеренно: половина инцидентов удлиняется не поломкой, а
действием, которое казалось очевидным.

Первые тридцать секунд любого инцидента:

```sh
curl -s localhost:8000/healthz | python -m json.tool     # роль, кеш, задачи, бэкап
curl -si localhost:8000/readyz | head -1                 # 200 или 503
systemctl status cookie-api cookie-scheduler --no-pager | head -20
tail -100 /opt/cookie/cookie.log | grep -i error
```

Идентификатор запроса (`X-Request-Id`) есть в ответе и в каждой строке лога —
жалоба игрока со скриншотом превращается в `grep` по одному значению.

## 1. Redis лёг

**Как понять.** `cache_backend_up == 0`. В `/healthz` поле `cache` не `redis`.
В логе — `лимитер: redis недоступен`.

**Что происходит на самом деле.** Игра работает. Ломаются три вещи, и все три
тихие:

- лимитер уходит в память процесса — при `WEB_CONCURRENCY=N` фактический лимит
  становится N-кратным;
- метрики перестают сводиться между процессами, `/metrics` показывает 1/N
  трафика, каждый раз другую;
- фоновые задачи **не выполняются вовсе** — замок берётся fail closed. Это
  сделано намеренно: пропущенный проход дешевле, чем два ролловера сезона.

**Сейчас.**

```sh
systemctl status redis
redis-cli ping
journalctl -u redis -n 50 --no-pager
systemctl restart redis
```

**Чего не делать.** Не перезапускать `cookie-api`: процессы переживают падение
Redis и подхватят его сами. Не «чинить» задачи ручным запуском, пока Redis
лежит, — замка нет, и второй процесс сделает то же самое одновременно.

**Убедиться.** `cache_backend_up == 1`, затем через 15-20 минут —
`job_last_ok_age_seconds{job="notify_pass"}` снова меньше часа. Если задачи не
пошли, проверить, что жив `cookie-scheduler`: замок он берёт, но выполняет
только при живом Redis.

## 2. База не отвечает

**Как понять.** `/readyz` отдаёт **503**, `/livez` — 200. В логе
`readyz: база недоступна`. Растёт `http_requests_total{status="500"}`.

**Сейчас.**

```sh
systemctl status postgresql
psql "$DATABASE_URL" -c "SELECT 1"
# кто держит блокировки и кто висит дольше минуты
psql "$DATABASE_URL" -c "SELECT pid, state, wait_event_type, query_start, \
  left(query, 80) FROM pg_stat_activity WHERE state <> 'idle' \
  ORDER BY query_start LIMIT 20"
df -h /var/lib/postgresql          # кончившееся место выглядит как «база легла»
```

Место кончилось — сначала освободить (старые снимки в `backups/`, логи), потом
всё остальное. PostgreSQL на полном диске не чинится перезапуском.

**Чего не делать.** Не перезапускать приложение по кругу: `/livez` не зависит
от базы именно поэтому — перезапуск базу не чинит, а принятые запросы и
прогретые соединения теряет. Не убивать `pg_stat_activity` наугад: убитый
`autovacuum` вернётся, а убитая транзакция игрока — нет.

**Убедиться.** `/readyz` = 200, `rate(db_tx_retries_total)` вернулся к фону.
Отдельно посмотреть `db_dirty_connections_total`: любой прирост означает, что
у кого-то залипла транзакция, и такое соединение выброшено — если счётчик
растёт постоянно, это не инцидент базы, а инцидент кода.

## 3. SQLite: «database is locked»

**Как понять.** В логе `database is locked`, растёт `db_tx_retries_total`,
p99 на записи в секундах.

**Что это.** У SQLite **один писатель на файл**. Несколько воркеров на одной
машине выстраиваются в очередь за блокировкой, и никакой код это не ускорит.

**Сейчас.** Снизить `WEB_CONCURRENCY` до 1 — вернёт отзывчивость немедленно.
Настоящее решение одно: `DATABASE_URL`, то есть PostgreSQL (переезд —
`migrate_to_postgres.py`, порядок в README).

## 4. Платежи: звёзды списались, товара нет

**Как понять.** Жалоба игрока либо `/api/admin/payments` со статусами:

| Статус | Что это |
|---|---|
| `unmatched` | платёж пришёл, но товара с таким кодом в конфиге нет |
| `void` | выдать нечего (товар убрали из конфига после оплаты) |
| `paid` дольше часа | инвойс оплачен, начисление не завершилось |

**Сейчас.**

```sh
grep -F "<charge_id>" /opt/cookie/cookie.log      # весь путь платежа
curl -s localhost:8000/api/admin/payments -H "Authorization: tma <initData>"
```

Начисление идемпотентно по `charge_id`: повторная выдача не удвоит товар.
`unmatched` чинится возвратом кода товара в `game_config.py` и перезапуском —
после него платёж досчитается сам.

**Чего не делать.** Не начислять руками через `UPDATE users`: книга операций
не увидит начисления, сверка `economy.drift_report()` начнёт ругаться на этого
игрока каждый день, и настоящую дыру в ней уже не разглядеть. Выдавать —
только через игровую логику.

**Возврат.** Возврат звёзд обрабатывается и откатывает выданное. Если игрок
успел потратить — баланс уйдёт в минус, это ожидаемо и видно в
`SELECT COUNT(*) FROM users WHERE cookies < 0`.

## 5. Откат релиза

**Штатный путь** — канарейка сама: `deploy/canary.py release` откатывается по
метрикам, ничего делать не нужно.

**Уже выкатили на всех, и стало плохо:**

```sh
python deploy/canary.py rollback --main      # вернуть парк на прошлый sha
python deploy/canary.py status               # что где стоит сейчас
```

Прошлый sha лежит в `/opt/cookie/.canary-state.json`, записан ДО переключения.
Файла нет — руками:

```sh
git -C /opt/cookie checkout --detach <sha>
/opt/cookie/venv/bin/pip install -q -r /opt/cookie/requirements.txt
systemctl restart cookie-api cookie-scheduler
```

**Единственное, что откат кода НЕ вернёт, — схему базы.** Миграции идут вперёд
и только вперёд. Если релиз их накатил, откат кода даёт старую версию на новой
схеме; сработает это или нет, зависит от того, была ли миграция совместимой.
Не сработало — `RUNBOOK.md`, сценарий 3 (восстановление на точку во времени, с
остановкой сервиса).

**Чего не делать.** Не выкатывать «быстрый фикс» поверх сломанного релиза.
Откат возвращает известное состояние, фикс даёт неизвестное — а разбираться
приходится под нагрузкой и с испорченными данными.

## 6. Канарейка застряла

Скрипт упал между шагами — трафик может идти на процесс, за которым уже никто
не следит. Проверить и снять руками:

```sh
cat /etc/nginx/conf.d/cookie-upstream.conf     # есть ли строка про :8001
python deploy/canary.py weight 0               # убрать её и перезагрузить nginx
systemctl stop cookie-canary
```

Порядок обязателен: сначала снять вес, потом гасить процесс. Наоборот — это
пачка `502` у игроков, которые как раз попали на канарейку.

## 7. Telegram не отвечает

**Как понять.** Растёт `notifications_total{result="fail"}`, в логе таймауты к
`api.telegram.org`. Игра при этом работает: Mini App ходит на наш домен.

**Сейчас.** Ничего. Пуши и платежи ретраятся, отправка не блокирует запросы
игрока. Проверить, что это именно Telegram, а не мы:

```sh
curl -s -o /dev/null -w "%{http_code} %{time_total}\n" \
  "https://api.telegram.org/bot$BOT_TOKEN/getMe"
```

**Отдельный случай — webhook.** Если `BOT_MODE=webhook` и апдейты перестали
приходить, дело обычно в адресе, а не в Telegram:

```sh
curl -s "https://api.telegram.org/bot$BOT_TOKEN/getWebhookInfo" | python -m json.tool
```

Смотреть `last_error_message` и `pending_update_count`. Планировщик проверяет
подписку на webhook сам, но после переезда домена ему нужен верный
`WEBHOOK_BASE`.

**Чего не делать.** Не переключаться на поллинг «на время»: при `ROLE=api` +
`ROLE=scheduler` поллинг не поднимает никто, а `getUpdates` рядом с активным
webhook отдаёт ошибку.

## 8. Наплыв: всё живо, но медленно

**Как понять.** `http_requests_in_flight` растёт, p99 растёт, 5xx нет или
почти нет. `db_tx_retries_total` растёт — упёрлись в базу.

**Сейчас, по порядку дешевизны:**

1. `WEB_CONCURRENCY` вверх (на PostgreSQL; на SQLite это сделает хуже, см. §3);
2. вынести `scheduler` на отдельную машину — он уже отдельный процесс;
3. смотреть, КАКАЯ ручка тормозит: `/metrics`, `http_request_duration_seconds`
   по метке `route`. Лидерборд и состояние — разные болезни.

**Чего не делать.** Не поднимать лимиты в `/api/*`, чтобы «пропустить больше»:
лимитер тут не причина очереди, а единственное, что не даёт ей стать лавиной.

## 9. Неверный ивент

**Как понять.** Жалобы «где мой x2» или, наоборот, всплеск дохода на графиках
в выходные. `EVENTS`/`EVENT_WEEKDAYS` в `server/game_config.py` не совпадают с
тем, что видит игрок в UI.

**Что это на самом деле.** Ивент **детерминирован от календаря**: ни таблицы,
ни фоновой задачи, ни ручного включения нет. Неверный ивент — это всегда
неверная константа в `game_config.py`, приехавшая релизом. Значит, инцидент
чинится откатом кода, а не правкой данных.

```sh
grep -n -A6 "^EVENTS = " /opt/cookie/server/game_config.py
git -C /opt/cookie log --oneline -5 -- server/game_config.py
```

**Сейчас.** Правка константы + `systemctl restart cookie-api cookie-scheduler`,
либо откат релиза целиком (§5), если конфиг приехал вместе с кодом.

**Чего не делать.** Не править `EVENTS` посреди активного окна ради «быстро
поднять множитель». Снимка конфига на старте ивента ещё нет (п.9 плана), и
множитель применяется в момент начисления — правка на живом ивенте
пересчитывает не будущее, а поведение уже идущих сессий: два игрока за один
календарный день получают разное за одно и то же действие, а разобрать это
потом по логам нечем. Дождаться конца окна.

**Убедиться.** После рестарта — `/healthz`, затем один запрос состояния за
живого игрока: в ответе должен быть ожидаемый ключ ивента и множитель. Разбор
задним числом — по `economy_ledger` за окно выходных.

**Известное ограничение.** Kill switch для ивента отсутствует: погасить ивент
можно только релизом. Пока это так, единственная быстрая ручка — откат.

## 10. Компенсация: одному игроку и когорте

Сюда приходят из §4 (платёж потерян), §5 (откат отнял прогресс), §9 (неверный
ивент) и из `RUNBOOK.md` (восстановление из копии). Инцидент разный, порядок
один.

**Правило, которое нельзя обойти.** Начислять `UPDATE users SET cookies = ...`
нельзя никогда — об этом же §4. Раньше это было обещание; теперь это свойство
инструмента: единственный путь выдачи — ручка ниже, а она умеет только звать
денежные примитивы, пишущие в книгу той же транзакцией. Прямого доступа к
колонке баланса в `server/support.py` нет вовсе.

**Сначала посмотреть на игрока.** Одна ручка вместо пяти запросов:

```sh
curl -s "localhost:8000/api/admin/player/<user_id>"      -H "Authorization: tma <initData>" | python -m json.tool
```

В ответе: цепочка `invoice -> payment -> grant -> refund` по каждому платежу с
подтянутыми движениями книги, сама книга, сверка (`reconcile`), уже выданные
компенсации и флаги. **Пустой `ledger` у платежа со статусом `fulfilled` — это
и есть «звёзды списались, товара нет».** Ненулевой `drift` в `reconcile`
означает, что этому игроку уже кто-то начислял мимо книги: разбор надо начинать
с этого, а не с текста обращения.

**Одному игроку.**

```sh
curl -s -X POST localhost:8000/api/admin/compensate   -H "Authorization: tma <initData>" -H "Content-Type: application/json"   -d '{"user_id": 123, "currency": "cookies", "amount": 5000,
       "reason": "support_payment_lost", "incident": "2026-08-07-stars",
       "note": "тикет #12"}'
```

`reason` — только из списка (`GET /api/admin/compensate/reasons`); свободный
текст ручка не примет. Это не бюрократия: причина уезжает в книгу, по ней потом
считают стоимость инцидента, и один инцидент под четырьмя формулировками
посчитать нельзя.

`incident` — метка, она же ключ идемпотентности. **Повтор с той же меткой
ничего не начислит второй раз** (`already_paid: true`), поэтому на вопрос «а
точно прошло?» правильный ответ — выполнить ещё раз.

**Когорте.** Список пострадавших берётся ИЗ ДАННЫХ, а не из жалоб: пожаловалось
меньшинство. Сначала посмотреть, кого задело:

```sh
curl -s -X POST localhost:8000/api/admin/compensate/cohort   -H "Authorization: tma <initData>" -H "Content-Type: application/json"   -d '{"kind": "purchase_status", "value": "unmatched",
       "since": 1786000000, "until": 1786100000}'
```

`kind`: `ledger_reason` (движение с такой причиной в окне — основной способ,
что бы инцидент ни сломал, след остаётся в книге), `purchase_status`
(`unmatched` / `void` / `paid` — прямо таблица из §4), `analytics_event` (для
того, что в книге следа не оставило).

Потом выдача. **`dry_run` по умолчанию `true`, и первый прогон обязан быть
сухим:** массовая раздача — единственное необратимое действие в админке, книга
append-only и отнять выданное нечем.

```sh
# 1. сухой прогон: сколько человек и сколько всего
curl -s -X POST localhost:8000/api/admin/compensate/bulk ...   -d '{"cohort": {"kind": "purchase_status", "value": "unmatched"},
       "currency": "cookies", "amount": 5000, "reason": "support_payment_lost",
       "incident": "2026-08-07-stars"}'
# 2. посмотреть на cohort_size и total. Не сходится с ожиданием — не платить
# 3. тот же запрос с "dry_run": false
```

Оборвалось на середине — просто повторить: платится каждый своим токеном из
(инцидент, валюта, игрок), уже получившим второй раз не достанется.

**Чего не делать.** Не компенсировать «на глаз всем активным»: когорта из
селектора воспроизводима и объяснима, когорта из головы — нет, а объяснять
придётся через месяц по графику выручки. Не выдавать `count_earned` (ручка и не
даёт): компенсация, попавшая в заработок, поднимает игроку уровень и место в
таблице лидеров за нашу же ошибку.

**Убедиться.** `GET /api/admin/player/<user_id>` — компенсация видна в
`compensations`, `reconcile` по-прежнему без расхождения. Стоимость инцидента
целиком:

```sql
SELECT reason, COUNT(*), SUM(amount) FROM economy_ledger
 WHERE ref_type = 'incident' AND ref_id = '2026-08-07-stars' GROUP BY reason;
```

## 11. Подозрительный аккаунт

**Как понять.** Жалоба на игрока, аномалия в таблице лидеров, всплеск выдачи по
рефералам либо плановый просмотр:

```sh
curl -s localhost:8000/api/admin/fraud -H "Authorization: tma <initData>"   | python -m json.tool
```

Списки и что каждый значит:

| Флаг | Что значит |
|---|---|
| `ledger_drift` | баланс не объясняется книгой: потерянный апдейт **или** ручное начисление |
| `click_rate` | кликов/час выше физического потолка `MAX_CPS` — обход лимитера |
| `referral_burst` | 10+ приглашений за час |
| `referral_dead` | приглашённые не сделали ни клика, ни слияния — ферма аккаунтов |
| `refund_series` | 3+ возврата Stars |
| `refund_debt` | возврат забрал больше, чем было: выданное успели потратить |

**Сейчас.** По конкретному игроку — `GET /api/admin/player/<user_id>`: там те же
флаги плюс книга, по которой видно, чем именно набран баланс.

**Чего не делать.** Не блокировать по флагу. Автоматических блокировок здесь нет
намеренно: каждое правило ловит и честные случаи (щедрый игрок позвал семью,
кто-то действительно играет по десять часов), а блокировка платящего игрока по
эвристике стоит дороже любого фрода. Флаг — повод посмотреть книгу, не приговор.

Не «откатывать» набранное прямым `UPDATE`: это тот же запрет из §4, только со
знаком минус, и он оставит вечное расхождение в сверке. Списание, если оно
всё-таки нужно, делается денежным примитивом с причиной — то есть кодом, а не
рукой в psql.

**Убедиться.** После разбора `ledger_drift` по игроку обязан быть пуст. Если он
не пуст и после — значит, дыра в коде, а не во фроде, и это уже §2 плана
наблюдаемости, а не работа поддержки.

## 12. Аналитика: выгрузка встала

**Как понять.** `analytics_export_backlog` растёт, в логе
`аналитика: удалено N сырых событий, которые так и не были выгружены`, либо:

```sh
cd /opt/cookie && venv/bin/python tools/export_analytics.py --status
```

**Что происходит.** Сырые события удаляются по TTL **только после выгрузки**
(`analytics_events.exported_at`). Пока выгрузка стоит, таблица растёт — это
терпимо. Нетерпимо другое: по истечении `EVENTS_TTL_DAYS + ANALYTICS_EXPORT_
GRACE_DAYS` невыгруженное всё же удаляется, и вот это уже безвозвратная потеря
данных, которую заметят через квартал по расхождению в отчётах.

**Сейчас.** Запустить выгрузку руками и посмотреть на ошибку:

```sh
cd /opt/cookie
venv/bin/python tools/export_analytics.py --out /var/lib/cookie/analytics
df -h /var/lib/cookie          # место кончилось — самая частая причина
systemctl list-timers | grep analytics
```

Порядок в самом скрипте безопасный: файл ложится на диск и синхронизируется
ДО подтверждения, поэтому падение в любой точке означает лишний повтор партии,
а не дыру. Повтор безвреден — у каждой строки есть `event_id`.

**Чего не делать.** Не «расчищать таблицу» руками (`DELETE FROM
