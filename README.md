# 🍪 Cookie Merge — Telegram GameFi Mini App

Merge-игра с кликером, уровнями, батл-пассом, рефералкой и покупками за Telegram Stars.

## Структура

```
bot/                  # aiogram: /start + оплата Stars + пуши
├── loader.py
├── notifier.py       # фоновые пуш-уведомления (энергия/ферма/стрик), макс 1 в ~20ч
└── handlers/         # start.py (кнопка Mini App, deep-links), payments.py (Stars)
server/               # FastAPI
├── auth.py           # валидация tg initData (HMAC), tg_user/tg_admin dependencies
├── game_config.py    # ВЕСЬ игровой баланс (крутить числа здесь)
├── game_logic.py     # энергия, XP, сезоны, дейлик, квесты, реф-майлстоуны
└── routers/
    ├── game.py       # /api/state, кликер, merge, уровни, ачивки, дейлик, квесты
    ├── meta.py       # /api/auth, рефералка+майлстоуны, промо, БП, магазин, канал
    └── admin.py      # /api/admin/* — промо, source, статистика, рассылка
db.py                 # SQLite + авто-миграция схемы
webapp/               # React + Vite + TS (Mini App), собирается в webapp/dist
main.py               # бот (polling) + API (uvicorn) + notifier одним процессом
```

## Запуск

1. Заполни `.env`:
   ```
   BOT_TOKEN = "токен от @BotFather"   # старый токен засветился — перевыпусти!
   ADMIN_ID = 1076078800
   BOT_USERNAME = "имя_бота_без_@"     # для реф- и source-ссылок
   WEBAPP_URL = "https://<твой-туннель-или-домен>"
   PORT = 8000
   CHANNEL_USERNAME = "имя_канала"     # опционально: награда за подписку в профиле
   ```
2. Собери фронт: `cd webapp && npm install && npm run build`
   (для реф-ссылок на фронте: `VITE_BOT_USERNAME=имя_бота npm run build`)
3. `python main.py` — поднимет бота и API на :8000, фронт раздаётся с корня.
4. Для теста в Telegram нужен HTTPS: `cloudflared tunnel --url http://localhost:8000`
   (или ngrok), полученный URL → в `WEBAPP_URL` **и** в настройки Mini App у @BotFather
   (/newapp или кнопка меню бота).

## Деплой

Один процесс (`ROLE=all`, поллинг) остаётся рабочим вариантом и дефолтом. Когда
онлайна становится больше, чем тянет один процесс, роли разъезжаются:

| Роль | Что несёт | Сколько копий |
|------|-----------|---------------|
| `api` | HTTP, Mini App, приём webhook-апдейтов | `WEB_CONCURRENCY` |
| `scheduler` | ролловер сезона, бэкап, чистки, пуши, проверка webhook'а | ровно одна |

При `WEB_CONCURRENCY > 1` `main.py` становится мастер-процессом: открывает
слушающий сокет, раздаёт его N воркерам и следит, чтобы упавший поднялся
заново. Воркеры поднимают ТОЛЬКО ASGI-приложение — фоновых задач у них нет ни у
одного, поэтому `ROLE=api` тут обязателен, а всё остальное старт отменяет.

Три вещи, без которых несколько процессов ломают игру, а не масштабируют её, и
все три проверяются в `settings.problems()` до старта:

- `REDIS_URL` — лимитер запросов и владение фоновыми задачами общие. В памяти
  процесса лимит стал бы N-кратным.
- `BOT_MODE=webhook` — `getUpdates` отдаёт апдейт одному подписчику, так что
  второй процесс на поллинге не удвоил бы бота, а начал воровать апдейты.
- `DATABASE_URL` — на SQLite писатель в файле один, и воркеры будут ждать друг
  друга на блокировке (это предупреждение, а не отказ).

Юниты systemd лежат в `deploy/`: `cookie-api.service` и
`cookie-scheduler.service`, оба читают общий `/opt/cookie/.env`, роль задают
через `Environment=`.

```
sudo cp deploy/cookie-*.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now cookie-api cookie-scheduler
systemctl status cookie-api cookie-scheduler
```

Логи при нескольких воркерах пишутся в отдельный файл на процесс
(`cookie.<pid>.log`): ротация — это переименование, и N процессов, ротирующих
один файл, теряют часть записей.

## Как что работает

- **Авторизация** — фронт шлёт `Authorization: tma <initData>`, сервер проверяет
  HMAC-подпись токеном бота. Сервер — источник правды: клики батчами с CPS-лимитом
  и энергией, все merge-ходы валидируются на сервере.
- **Экономика** — три правила, на которых держится прогрессия (всё в `game_config.py`):
  1. *Уровни нельзя купить.* Рядовой мердж даёт копейки XP (кап
     `MERGE_VOLUME_XP_CAP`), основной XP — **личный рекорд тира**: первый предмет
     каждого уровня, разово, `best_item_level` в БД. Печеньками рекорд не
     ускоришь. Раньше XP шёл за каждый мердж, а дерево мерджа устроено так, что
     любая награда за слияние умножается на число спавнов — уровни покупались.
  2. *Мердж дохода-нейтрален.* `PASSIVE_GROWTH = 2.0` ровно равен ветвлению
     дерева: два предмета дают столько же, сколько один слитый. При 2.15
     окупаемость падала с 4.8ч до 1.05ч — доска разгоняла сама себя.
  3. *Клик — доля дохода, а не своя экспонента.* `click_power` считается от
     дохода фермы и доски (`CLICK_SHARE_BASE`), поэтому не отрывается в
     самостоятельный триллион и не умирает на поздних уровнях; тап во всю силу
     примерно равен пассивному доходу.

  Сложность крутится одной ручкой — `ITEM_PAYBACK_HOURS` (за сколько часов
  окупается предмет на доске). Проверяется `balance_sim.py` (`python balance_sim.py 336`).
- **Рефералка** — ссылка `t.me/<bot>?startapp=ref_<user_id>`, взаимная награда
  начисляется обоим при первом входе приглашённого.
- **Source-ссылки** — создаются в админ-вкладке (`t.me/<bot>?startapp=src_<code>`),
  регистрации по ним видны в статистике.
- **Промокоды** — создаются в админ-вкладке, активируются в профиле (1 раз на юзера).
- **Stars** — `/api/shop/invoice` создаёт invoice-ссылку, фронт открывает её через
  `openInvoice`, начисление в `bot/handlers/payments.py` после `successful_payment`
  (идемпотентно по charge_id).
- **Админ-вкладка** появляется в Mini App автоматически, только если ты зашёл
  с аккаунта `ADMIN_ID`. Там же — рассылка всем игрокам (кнопка «Тест» шлёт превью себе).
- **Ежедневная награда** — попап при входе, стрик 7 дней (500→15 000 🍪),
  пропуск дня сбрасывает стрик. День считается по UTC.
- **Ежедневные задания** — 3 в день (выбор детерминирован датой, у всех одинаковые),
  награда: печеньки + XP батл-пасса. Прогресс копится в кликах/мерджах/покупках.
- **Сезоны** — 14 дней (`SEASON_EPOCH`/`SEASON_LENGTH_DAYS` в game_config).
  Лидерборд ранжируется по `season_earned` внутри своей лиги (лига — по уровню),
  топ-10 каждой лиги получают призы (`SEASON_TOP_REWARDS`). Массовый ролловер идёт
  по таймеру из `notifier`; в запросе игрока сбрасывается только его собственная
  строка (`ensure_user_season`) — раньше каждый запрос сканировал всю таблицу.
- **Реф-майлстоуны** — 3 друга → буст x2 на 24ч, 10 → эксклюзивный скин 👑,
  25 → Premium Пасс. Забираются в профиле.
- **Пуши** — `bot/notifier.py` раз в 15 мин проверяет всех: стрик сгорает / ферма
  упёрлась в кап / энергия полная. Максимум 1 пуш в ~20ч, активным (были онлайн
  < 3ч назад) не шлём, заблокировавших бота помечаем и пропускаем.
- **Золотая печенька** — сервер планирует появление (раз в 3-7 мин игры, живёт 12с),
  клиент рисует 🌟 и репортит тап. Эффекты: frenzy x7 на 25с или мгновенный бонус.
- **Комбо** — тапаешь без пауз (>=3 кликов/с) — множитель растёт до x2,
  пауза 4с сбрасывает. Считается на сервере по батчам.
- **Престиж** — после 10M заработанных: сброс прогресса (скины/друзья/ачивки/Stars
  сохраняются) за очки = sqrt(earned/1M), каждое очко даёт +30% ко всему доходу
  навсегда. 40% уровня переживает сброс, иначе заново проходить все `req_level`,
  а множитель этого не ускоряет.
- **Закваска (оффлайн-рецепты)** — перед выходом игрок ставит тесто: длиннее
  рецепт — выше множитель оффлайн-дохода, но уже окно возврата. Рано — не
  поднялось, поздно — подгорело. `RECIPES` в game_config.
- **Ивенты выходных** — суббота и воскресенье дают глобальный множитель на
  активный доход. Расписание выводится из календаря, как номер сезона: ни
  таблицы, ни фоновой задачи, ни ручного включения.
- **Дуэли** — асинхронный забег 1x1 на сутки внутри своей лиги. Метрика —
  заработок ЗА дуэль, приз считается от дохода победителя. `server/duels.py`.

## Эксплуатация

- **Бэкапы** — `notifier` раз в сутки делает горячий снимок в `backups/` и
  хранит неделю (`BACKUP_INTERVAL_H`, `BACKUP_KEEP`). Движок выбирает
  `db.snapshot`: sqlite backup API или `pg_dump --format=custom` (нужен
  `postgresql-client` в PATH, иначе снимок пропускается с записью в лог).
- **PostgreSQL** — второй диалект той же схемы. Включается заполненным
  `DATABASE_URL` (`DATABASE_PATH` при этом игнорируется), нужен драйвер
  `psycopg[binary]` из `requirements.txt`. Схема одна: она написана на типах
  SQLite, а перевод (`INTEGER PRIMARY KEY` → `BIGSERIAL`, `REAL` → `DOUBLE
  PRECISION`, триггеры → PL/pgSQL) делает `db.py`. Переезд:
  `DATABASE_URL=postgresql://... python migrate_to_postgres.py --sqlite data.db
  --dry-run`, затем без `--dry-run`. Скрипт открывает SQLite только на чтение,
  требует пустой приёмник (иначе `--force`), переносит журнал `schema_migrations`
  и догоняет последовательности. Перевод схемы проверяет `test_dialect.py`;
  живые проверки включаются `TEST_DATABASE_URL`.
- **Логи** — INFO с ротацией в `LOG_FILE` (по умолчанию `cookie.log`, 5 МБ x3).
  При `WEB_CONCURRENCY > 1` каждый процесс пишет в свой `cookie.<pid>.log`:
  ротация — это переименование, и N процессов теряли бы на ней записи.
  `LOG_JSON=1` переводит вывод в JSON — одна строка, один объект.
- **Наблюдаемость** — `server/obs.py`. У каждого запроса свой идентификатор
  (`X-Request-Id`: свой или присланный прокси), он подставляется фильтром в
  КАЖДУЮ строку лога вместе с `user_id`, `role`, `pid` — включая строки
  игровых модулей, которые про HTTP не знают. Метрики отдаёт `/metrics` в
  формате Prometheus под `METRICS_TOKEN`. Процессы досылают свои приросты в
  Redis (`HINCRBYFLOAT`) раз в 10 секунд и на остановке, а `/metrics` отдаёт
  сумму по всем: слушающий сокет один, scrape попадает в случайный воркер, и
  без сведения цифра была бы 1/N трафика, каждый раз другая. Без Redis всё
  остаётся в памяти (одиночный запуск). `SENTRY_DSN` включает отправку
  трейсбеков (`pip install sentry-sdk`; тело запроса не отправляется — в нём
  initData, то есть действующий пропуск в чужой аккаунт).
- **Проверки состояния** — три разные ручки, и путать их нельзя:
  `/livez` не трогает ничего (по ней ПЕРЕЗАПУСКАЮТ: упавшая на минуту база не
  повод перезапустить все воркеры), `/readyz` проверяет базу и отвечает **503**
  кодом (по ней ВЫВОДЯТ ИЗ БАЛАНСИРОВКИ; Redis отказом не считается — лимитер
  уходит на фолбэк), `/healthz` — подробный ответ для человека: роль, кеш,
  возраст фоновых задач. Остановка ждёт добитые запросы `GRACEFUL_TIMEOUT`
  секунд.
- **На что заводить алерты** (по метрикам `/metrics`):
  | Условие | Что это значит |
  |---|---|
  | `rate(http_requests_total{status=~"5.."})` > 1% пять минут | ручка сломана |
  | p99 `http_request_duration_seconds` > 2 с | база или воркеры не тянут |
  | `job_last_ok_age_seconds{job="db_backup"}` > 2 суток | бэкапов нет |
  | `job_last_ok_age_seconds{job="notify_pass"}` > 1 часа | планировщик умер |
  | `cache_backend_up == 0` при нескольких воркерах | лимит стал N-кратным |
  | `rate(db_tx_retries_total)` растёт | писатели дерутся за базу |
  | `economy_minted_total` скачком без роста игроков | дыра в начислении |
  | `economy_ops_total{result="replay"}` > 5% от `new` | клиенты теряют ответы |
  | `notifications_total{result="blocked"}` растёт | бота массово блокируют |
- **Preflight** — старт отменяется при отсутствующем `BOT_TOKEN` и при
  `DEV_MODE=1` на https-домене (бот публикует в чат рабочую подписанную ссылку).
- **Лимиты** — на игрока: `/api/state` 40/мин, тяжёлые ручки 20/мин, инвойсы
  5/мин, промокоды 10/час. Тело запроса ограничено 64 КБ, initData — 4 КБ.
- **Проблемные платежи** — `/api/admin/payments`: статусы `unmatched` (платёж не
  сошёлся с конфигом), `void` (выдать нечего), зависшие в `paid` дольше часа.
  Возврат звёзд обрабатывается и откатывает выданное.

## Дев-режим фронта

`cd webapp && npm run dev` — Vite-прокси кидает `/api` на :8000.
